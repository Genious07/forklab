# ForkLab audit and design update

Reviewed September 7, 2026 against the supplied implementation inventory and the
ForkLab blueprint. The existing main commit a3a73d2 had green CI and 54 passing
Python tests. That did not establish end-to-end correctness: a baseline-only run
completed on the server and crashed the entire React page in the browser.

## Result

The simulator, API, worker, CLI and web workbench form a functioning internal
prototype. This update fixes several correctness failures, adds regression tests,
and introduces an original SVG visual identity. It does not turn the prototype
into the complete public, multi-tenant product described in the blueprint.

## Findings fixed

| Problem | Change |
| --- | --- |
| Baseline report crashed comparison rendering | Typed single-arm report and comparison guard; baseline order inspection works |
| UI fetched only 500 of 650 orders, inspector exposed only 60 | API offset pagination, client fetches all pages, searchable 25-row inspection pages |
| Packed orders missing cutoff counted as dispatched | Separate held stage; dispatch requires a dispatch event |
| Future stock shortages visible when scrubbing backward | Shortage timestamps; label explicitly describes recorded historical shortages |
| Lost stream could leave run busy forever | Repeated durable-state polling with cleanup and refresh restoration |
| Results and order traces could belong to old selections | Effect cleanup, reset on run/dataset/arm changes, typed durable restoration |
| Imported scenarios could not be selected in the workbench | CSV import form, validation feedback and dataset selector |
| Demo reset could overwrite historical or other-organization snapshots | Immutable scenario writes and new demo snapshot IDs |
| Duplicate imports produced server errors | Validation errors; per-file 2 MiB and 5,000-order import limits |
| Idempotency keys could silently refer to different requests | Payload comparison, 409 conflict and database uniqueness |
| Stale workers could update or finish another worker's job | Conditional ownership/lease fences, renewal during long seeds |
| Reports simulated every seed twice | Assemble directly from persisted metric checkpoints |
| Only the first seed was invariant checked | Check every seed and reject failed stored checkpoints |
| Cancellation late in execution could become success | Cancellation checked at terminal write; atomic cancel update |
| Concurrent assignments could over-reserve stock | Reserve synchronously before the next picker assignment |
| Shift start was ignored | Assignment waits for shift opening; invariant coverage |
| Single-pair comparisons could claim improvements | Inconclusive verdict; low-sample and fixed-workload notes |
| Different workloads could masquerade as paired policy studies | Require identical workload and facility inputs |
| Frontend tooling had reported vulnerabilities | Vite 6.4.3; npm audit reports zero vulnerabilities |

Engine version is now forklab-sim-0.1.1. Historical runs remain attached to their
recorded version; replaying them under a different engine is not an exact replay.

## Visual design

The mark depicts one input branching into two orthogonal policy paths ending at
separate dispatch docks. Blue identifies baseline, orange candidate. Teal/red are
reserved for measured verdicts, always accompanied by text.

The workbench introduces a routing illustration for empty states, four warehouse
stage icons, policy editing beside the process on wide screens, workload selection,
shared time, three evidence interval graphics and searchable order traces. The
exact numeric table remains available beneath the visual summary. Layout reviewed
at the native desktop viewport and 390px width, with no document overflow at 390px.

Assets are in apps/web/public/brand; design rationale is in docs/design.md.

## Verification

- 68 Python tests pass, including simulator, API/import, statistics and worker recovery.
- Five Vitest tests pass for historical counts, full pagination and empty comparison rendering.
- TypeScript production build, Ruff lint/format and git diff whitespace checks pass.
- CLI verify passes hand arithmetic, invariants and deterministic event replay.
- CLI demo runs; a 10-pair decision manifest reproduces every metric exactly.
- Browser: baseline succeeds without blanking, all 650 orders load, EDF fork comparison
  completes 60 replications, refresh restores a running study, search opens the
  order event trace, export action succeeds without a console error.
- Imports are tested through the real API integration fixture, including run completion,
  duplicate IDs, estimated provenance and oversized files. Native file-picker
  interaction was not automated in the browser.
- npm audit reports zero vulnerabilities in installed dependencies.
- Compose configuration validates. Docker runtime and Postgres integration were not
  exercised because the local Docker daemon is unavailable. No public deployment
  was performed. Local browser review used a separate SQLite audit database.

## Changes still needed, in priority order

1. **Public deployment boundary:** replace the organization header stub with verified
   identity and roles; add quotas, proxy body limits, rate limits and admission control.
   Use authenticated private access for a pilot until this is done.
2. **Data lifecycle:** introduce Alembic migrations, test upgrades and backups on
   Postgres, and validate multi-worker process recovery under real database contention.
   This release adds unique indexes on startup; back up and check duplicate keys first.
3. **Time semantics:** define facility date, timezone and day origin. Legacy ISO imports
   discard date/offset. Use numeric minute offsets for the current single-day model.
4. **Statistical honesty:** empty timing samples currently serialize as zero; make them
   unavailable rather than numerical estimates. Timing metrics include only picked or
   dispatched orders. Throughput and unfulfilled outcomes must accompany them.
5. **Real-world validity:** calibrate against actual facility events and test on held-out
   days. Seed intervals describe one fixed workload, not general performance guarantees.
6. **Blueprint features:** calibrated-model editor, workload uncertainty, policy proposer,
   approval/decision workflow and richer scenario history remain future implementation.
   A constrained AI proposer should come after model validation, not substitute for it.

The useful near-term pilot is a private warehouse planning tool with explicit input
assumptions, reproducible policy comparisons and an operator who can validate the
model. The current evidence does not support autonomous operational decisions.
